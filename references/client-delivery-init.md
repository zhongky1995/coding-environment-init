# 客户交付工作区初始化

本分支用于建立或接手长期服务一个客户的项目工作区，承接资料整理、业务咨询、方案、设计、开发及验收等任务。交付的是已有事实、范围、材料和后续工作的可用入口；本轮没有开发任务时，不要求产品或运行环境就绪。

## 1 先读懂已有材料

接管前检查生效指令、已有目录、版本记录和未提交改动。按材料数量与当前目标选择读取方式，优先找出当前有效合作约定，再结合相关方案、会议和参考资料形成背景。文件名与摘要不代替正文，附件、表格及影响理解的图示也要读取；格式专属读取使用相应能力。

形成以下判断即可继续，不为补齐所有字段拖延建档：

| 内容 | 需要留下的判断 |
|---|---|
| 客户是谁、做什么 | 名称与主体确认状态，业务、使用者/决策者、主要场景及已知系统；人员身份不自行推断 |
| 为什么合作 | 当前问题、期望结果、合作阶段、客户可配合方式与已知限制 |
| 现在承诺什么 | 有效约定、已包含工作、交付/验收、价格和日期条件；无合同则记录现有共识与未确认项，不编造合同基线 |
| 有哪些不同层次的资料 | 正式约定及有效变更、历史方案、会议诉求、内部建议、参考工具、公开背景各自的作用 |
| 先做什么 | 用户明确的优先级，当前任务，待确认项及何时影响后续任务 |

用户明确某份是正式版本时，以此为起点梳理正文、附件及有效变更的适用关系。旧方案的预算、驻场安排、长期蓝图和竞品功能不自动进入当前承诺；会议细节可以成为需求证据，但不能冒充已签认变更。文件版本已敲定不等于已签署、生效、到账或验收。

遇到冲突，保留两边的原意、来源和需要解决的具体差异；有充分依据能分清适用范围时自行整理。缺少主体信息不阻塞其他建档，缺少设备参数也不阻塞资料归档；在相关任务真正依赖它时再处理。

必要公开检索以补当前业务判断为限，优先官方与可核验来源。记录链接、检索日期及能支持的有限结论；候选主体、宣传数据和现任关系不能仅凭转载变成客户已确认事实。不为建档检查全部账号或采集无关人员信息。

## 2 建立少量可持续维护的记录

先复用已有命名。下面是职责示例，不是必须逐个生成的文件清单；材料少时合并，工作线只有实际出现时再展开。

| 维护职责 | 典型内容与入口 |
|---|---|
| 用户总入口 | 项目目的、当前阶段、常用文件、怎么交新资料、如何接续任务；适合放根目录README |
| 客户与合作约定 | 客户背景、来源/确认状态，现行范围、合同或共识、优先级与重要缺口；复杂商务单独维护 |
| 原件与资料索引 | 原文件、版本和来源、接收/形成日期、保存位置，以及新旧材料之间的关系 |
| 当前工作线 | 实际开发/产品、咨询研究、方案汇报等工作的输入、当前成果和下一步；不预建所有未来模块 |
| 沟通、决定与变化 | 纪要、确认记录、范围或规则变化及其影响；不重复抄录原件 |
| 进展与交付 | 当前已完成/待做、下一具体动作；实际对客版本、交付和确认凭据、遗留项 |
| AI接续入口 | 如AGENTS，仅放当前工作入口、来源和更新规则；继承已有用户指令，不堆满客户资料 |

客户档案保留业务解释，合同/共识保存范围依据，当前进展保存执行状态；其他入口引用它们，避免多份可独立修改的同一结论。面向日常使用者用易懂目录名，不强制 `docs/ai`、PRD、architecture、QA或开发任务契约。

多条工作线并行时，明确当前优先级和仍需履行的其他工作；先做其中一项不等于删掉其余已约定成果。资料整理、本次用户交付、向客户发送、客户确认、最终验收分别记录。

若本轮包含软件开工准备或实现，复用此处客户事实和范围，在实际软件目录进入开发分支；不再复制另一套客户档案或全项目进度，也不因父目录是客户工作区就忽略其既有代码现场。只交付咨询、产品方案或设计稿时使用对应任务所需能力，不自动追加运行环境。

## 3 归档原件并留下新的资料入口

整理前确认是否需要移动文件。可以按合同、方案、会议、参考等类别归档，也可以保留原位并建立索引；保留现有链接及使用方式有价值时优先少移动。用户未要求拆分到其他平台时，就在当前工作区完成。

- 保留原内容和来源关系，同名新版本不能覆盖旧件。移动时记录原位置与新位置，对关键原件用大小/摘要等方式核对；已有可靠记录直接复用。
- 资料索引可用稳定编号或路径，不强制特定编号格式。最少能回答哪份材料、来自哪里、何时接收/形成、现在在哪里、是什么确认状态。
- 检索提取文本只是派生副本，注明原件和定位。有歧义回看原件，不能修改提取文本冒充客户更正；不默认将全部派生副本进版本库。
- 在根目录或总入口显眼位置留一个新资料接收入口，例如 `00-新资料入口/`；已有等价入口就复用。让用户能直接放文件、截图、会议记录或在线链接，不强迫先分类、命名或填表。补充说明模板可选。
- 说明后续接收动作：读取来源/版本/状态 → 检查是否重复或敏感 → 归档与登记 → 更新相关事实、需求、决定及进展 → 说明这批资料改变了什么。若要移动或清空接收目录，先确认已有可靠归档。
- 真实个人数据、凭据及大体积音视频按用途、授权和保存规则处理，不全量暂存未知资料。可以将待整理文件默认排除出Git并保留入口说明；忽略规则本身不代表备份或授权。

新资料入口是接收与整理约定；没有实际监控/自动化时，不宣称会自动处理、后台持续监听或定时提醒。

## 4 保存、核对和交接

用户已要求仓库初始化且边界明确时，可建立本地Git；先检查父仓库，避免嵌套。沿用可用身份和现行规则，保存前只核对本次内容；没有合适Git提交条件时用可验证文件快照，不伪造提交或修改用户全局身份。用户只要整理现有工作区时，也可以沿用其现有版本/备份机制。

核对实际结果：关键原件能打开且内容未被意外改写、资料索引与本地链接可达、旧/新范围没有混淆、确认状态没有升级失真、当前工作和新资料入口可找到、恢复点确实存在。简单工作区可以人工检查；只有重复价值明确时才加校验脚本，不能靠生成空文件或检查返回成功证明已完成。

最后交付总入口、客户/范围入口、当前进展和新资料入口，说明重要缺口会影响什么。客户工作区准备完成可以与软件尚未开始同时成立；不使用“应用未启动”把本轮判成未完成或受阻。

后续任务从现行AGENTS、整体合作目标、当前进展及相关工作线接续，核对现场后继续已授权工作。重要资料、决定或交付变化时按 [执行与接续](execution-and-handoff.md) 核对变更依据并更新原维护位置；本轮建议不能自行替换有效约定。普通回复无需反复重读全库。

## 分流示例

| 用户请求 | 适用处理 |
|---|---|
| 客户有全景方案、精简方案、正式合同和首次会议；先建档整理仓库，以后做开发和咨询，留新资料入口 | 本分支。读出版本关系、业务与有效范围，建立资料/工作线/接续入口；本轮不准备技术栈 |
| 新客户只有几段聊天，还没合同，先整理方便后面推进 | 本分支轻量处理；记录共识与未确认项，不要求虚构商务字段或生成整套空目录 |
| 仓库已有软件代码，这次只整理客户资料和项目交付记录 | 本分支，保护代码与既有约定，不顺手改运行环境 |
| 建客户交付仓库，并在本轮把报名页面实现到可试用 | 必要建档后进入开发分支并完成已授权实现；不能在文档建好后就停止 |
| 客户已建档，本次只把新会议并入需求台账 | 复用现有入口，做局部更新，不重复初始化或全量验收 |
