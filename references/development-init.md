# 软件开发初始化

仅在本轮确需软件开工准备、开发环境或已授权实现时读取。客户建档与长期交付工作区按 [客户交付初始化](client-delivery-init.md) 处理，不执行这里的环境准备或文档选档。

让下一轮开发从明确目标、可用仓库和可检验的约定开始。前置确认与仓库准备由 AI 执行并记录，用户只决定业务取舍与授权边界。

## 先判断这次要做什么

| 用户请求 | 执行范围 |
|---|---|
| 新项目开工、从想法开始准备 | 完成下面的前置准备和仓库初始化，交付第一批计划；没有业务开发授权时止于准备 |
| 接手已有项目 | 读取现行约定和相关代码，补影响下一批的缺口，保留已有结构、文档与工作区改动 |
| 初始化并实现某项功能 | 准备足够后按已有授权继续，不追加形式性的计划审批 |
| 继续已有任务或修一个局部问题 | 复用已完成的准备；无需重跑整个技能 |
| 只启动本地环境供用户试用 | 只启动和检查可访问性，不代跑测试套件或调用付费服务 |

技能不规定如何调度工作者。执行时依据用户要求、项目约定和实际能力选择；已有有效记录与职责保持连续，不另建第二套状态。

## 继承已有方案，补足开工条件

先读当前产物、有效需求与设计、相关代码和工作区状态。已有方案足以支持本批时直接准备环境并进入实现；缺少关键前提时按需参考 [开发前置确认](pre-development.md)，仅补会影响当前动作的部分。

问题理解与产品构思由相应能力承担，本技能不重复组织业务探索、功能推导和产品评审。技术事实主动查证，工程选择给出有依据的推荐；需要用户决定的业务取舍说明实际影响。能通过具体实现取得的信息可以在制作中完善，不要求全部文档先齐全。

按需从 [场景问题与示例](preflight-and-example.md) 定位账号、权限、数据或外部依赖等实际缺口，不逐项盘问所有类别。短实验可以借助最小环境先验证关键能力，相关访问和调用遵循已有授权。

## 仓库初始化：做到能开始开发

完整初始化和旧仓库接管时读取 [仓库准备流程](repository-setup.md)，按实际项目执行；仅要求文档骨架时记录未做的环境项，不扩大任务。

| 准备项 | 新项目 | 已有项目 |
|---|---|---|
| 目录与版本记录 | 确认真正项目根；适用时建本地 Git、忽略规则和可恢复起点 | 识别所属仓库/工作区、当前版本和未提交改动，不重置、不另造嵌套仓库 |
| AI 接手入口 | 按所用工具约定建立短入口（如 AGENTS.md），指向当前任务、规则和计划 | 保留现行指令和优先级，只补缺失导航 |
| 技术与运行环境 | 根据选定方案用框架惯例建立最小骨架、依赖与锁文件 | 复用实际框架、运行版本、包管理器与锁文件，不顺手升级 |
| 配置、数据、外部服务 | 提供无凭据配置示例、测试数据/身份和必要本地服务 | 核对开发连接目标，保护现有数据；无必要不操作正式环境 |
| 启动与检查 | 运行最小入口，确认能得到正常响应；建立适用检查入口并实际执行 | 复现当前相关启动/检查，记录既有失败和未验证部分 |
| 保存与交接 | 记录起点、命令、环境条件、证据和下一动作 | 仅保存本次相关变化，注明已有工作和未完成状态 |

初始化不等于部署。发布、付费调用、正式数据操作和创建远程仓库等遵循实际授权。没有 Git、凭据或可用运行环境时准确记录影响，只暂停依赖该条件的工作。

## 用少量文件承接结果

先看现有材料是否够用。已有 requirements、design、acceptance、plan、progress 等文档直接引用，保留命名；不为了模板复制一套。

| 档位 | 适用情况 | 缺失时补建 |
|---|---|---|
| minimal | 一个明确、可直接验证的小闭环 | docs/ai 下三个核心文件；执行现场放 current-task |
| guided | 日常多步、跨会话开发；默认推荐 | 三个核心文件 + docs/plan/current-todo.md |
| expanded | 本批确需单独维护详细需求、设计和验收方法 | guided + repo-map、PRD、architecture、QA |

| 内容 | 默认记录位置 |
|---|---|
| 项目用途、技术/运行入口、初始化证据、配置与测试身份获取方式 | project-context.md |
| 当前方案、数据/权限/模块规则、决定依据与变更权限 | architecture-guardrails.md；复杂细节链接现有设计 |
| 跨模块/批次的业务目标、判断规则、事实来源、成功与异常/停止口径 | 优先复用产品/业务规则文档，附代表性案例和验收关联；小项目可用 current-task 的稳定约定段并由入口链接 |
| 本批需求、范围、授权、验收定义、执行入口 | current-task.md |
| 内部步骤、进度、验证结果、决策变化和交接 | guided 的 current-todo.md；minimal 放 current-task |

每项事实只维护一处。expanded 的 PRD 保存详细需求依据，QA 描述检查方法并引用验收 ID；不能形成两套各自修改的标准与状态。新项目或模块多不单独构成升档理由，见 [选档决策卡](preset-decision-card.md)。

影响多个模块或后续批次的必要约定要落到项目文档，不只保存在聊天、派单或提示词里。记录依据、确认状态、适用范围与变更影响；临时进度不混入长期规则。规则变化时更新对应案例和验收，历史证据保留原适用版本。独立业务校验不要求新增角色或逐项审批，已有充分依据的局部修复直接复用。

### 文档脚本的职责

```bash
python3 scripts/bootstrap_repo.py /path/to/project --preset guided
```

脚本路径相对本技能目录。它只创建缺失文档和显式选择的目录，不会执行 Git 初始化、安装依赖、补业务内容或验证可运行性。Agent 仍须按前两节完成真实准备。已有同义文档时直接局部补充，无须运行脚本。

CLI 默认 minimal；默认保留现有文件。`--force` 是覆盖而非迁移，只用于明确要求重建且可覆盖的生成物。默认不用通用代码目录；仅绿地项目、用户明确要求且无框架布局时使用 `--mode greenfield --code-layout layered`。具体生成与迁移规则见 [生成物清单](scaffold-map.md)。

## 怎样宣布准备完成

在 current-task 的准备结论中给出：

- 第一批最终能完整使用什么，哪些业务决定与技术条件已成立。
- 仓库位置、启动/检查方式、保存点和实际验证证据入口。
- 内部步骤、验收对应、下一具体动作和必要阅读文件。
- 哪些项仍有缺口、影响什么、是否阻塞第一步；不相关项可标不适用。
- 已有授权覆盖到哪里，下一步可以直接执行还是确实需要用户决定。

用「可以开始本批 / 仅可先做某实验 / 被具体条件阻塞」说明结论。文件已生成、测试框架已存在、用户听懂方案都不能单独证明可以开工。所有必要条件已满足时停止准备，不追加无边界的审计。

## 后续执行和续接

准备足够后，按 [执行和交接](execution-and-handoff.md) 继续制作：从当前成果与决定理由接续，在实现中保住整体设计，沿用适用检查和现有记录。不要再把这些要求复制成一份项目流程。初始化只服务开工，成果质量由实际承担者持续判断和完善。
