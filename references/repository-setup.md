# 仓库准备流程

本文件用于软件开发分支的仓库与运行准备。客户交付资料仓库参见 [客户交付初始化](client-delivery-init.md)，不以应用启动、测试身份或框架依赖作为其完成标准。

本流程的完成标准是：第一步开发有正确位置、运行条件、反馈方法和可恢复的记录。生成 Markdown 只是其中一项。新项目完整准备，旧项目复用并补缺；用户只要文档或只要启动时按其范围执行。

## 1. 确认根目录和现有工作

检查项目文件、现行 AGENTS、说明文档、依赖清单与锁文件；用 Git 的仓库根、分支、当前提交和状态确认版本现场。目录在更大的父仓库内时先遵循现有仓库布局，不静默创建嵌套仓库。

已有代码但框架不明时按 existing 处理，定位入口再行动。记录未提交改动和归属，尤其是用户/其他任务正在进行的工作；不能用 reset、清理或覆盖来得到「干净起点」。

产物：project-context 的项目根、实际技术与入口；执行记录中的当前版本/未提交改动。无 Git 时如实记录，必要时用文件快照或摘要保留可恢复起点。

## 2. 建立本地版本记录和忽略规则

**新项目**：用户已要求初始化且项目边界明确时，可以建立本地 Git；复用用户已有身份配置。没有提交身份时保留文件并报告缺口，不修改全局身份。依据实际技术补 .gitignore，覆盖本地凭据、环境文件、依赖缓存和生成输出等不应归档的内容。

**已有项目**：沿用现有 Git 与分支约定，只补实际遗漏的忽略项。忽略规则不能清除已经跟踪的凭据或历史；发现这类问题如实记录并按影响处理，不擅自改写历史。

在有意义的准备节点保存本次已核对的文件；提交前检查暂存内容，避免把他人的未提交改动或真实凭据混进去。遵循现有提交授权；不能提交时保存明确的差异/快照位置。不要只写「已存档」而没有实际提交或快照。

产物：本地版本记录方式、可查到的起点和忽略规则。创建远程仓库、推送、公开代码与发布不是本地初始化的默认动作。

## 3. 建立 AI 接手入口

读取所有实际生效的上层/项目/子目录规则，保留其约束与优先级。已有入口只补导航；没有入口时，按实际使用工具建立一份简短项目入口，例如 AGENTS.md，不为所有可能的工具复制多份家规。

入口应指向：当前交付、有效边界、执行记录和必要运行说明。详细需求、调试过程、全部事故不堆进入口。新会话应能由它找到当前工作，不要求用户重贴历史。

产物：有效入口与可解析的路径。先查现有 requirements/design/acceptance/plan/progress 等文档，能复用就复用；脚本生成的是缺失骨架，不会理解任意自定义体系。

## 4. 准备与方案一致的最小技术环境

在关键技术方案已选定后执行。

**新项目**：采用实际框架的常规初始化方式，补本批需要的入口和配置。根据已选择的运行时/包管理器安装必要依赖，保留锁文件，固定可复现的启动方式。不要先凭空建立 modules/shared 等目录再让框架迁就它；用户明确需要无框架通用目录时才考虑 layered 模式。

**已有项目**：从配置、说明和锁文件确定运行版本、包管理器与安装命令，按锁文件恢复依赖；缺少条件时具体定位。不要把初始化变成运行时升级、换包管理器或全项目重构。

仅需要一个本地入口的项目，不为了「规范」搭微服务、容器集群或全套 CI。有明确复现收益时再加入对应工具。所有必需的外部资源/费用按本批授权处理。

产物：真实代码/框架入口、依赖/锁文件、必要运行版本与命令；不是只有 src 空目录。

## 5. 准备配置、测试数据和必要服务

- 用不含可用秘密的配置示例说明必填变量、用途与获取方式；真实凭据放合适的本地/平台凭据位置，避免写入版本化文件或日志。
- 核对数据库、存储、队列与外部服务的连接目标。为本批准备必要的本地/测试环境，演示数据不进入正式数据；已有系统不因试跑而清空数据库。
- 涉及持久化时准备适用的迁移/建表和测试样本。涉及角色/租户时建立足够验证允许与拒绝路径的测试身份，记录获取/生成方式，不生成带密码的文档表。
- 外部调用区分模拟、服务商测试环境、真实调用。使用真实付费接口、通知收件人或正式数据必须在相应授权内；缺少权限时继续独立工作并标注真实集成未验证。
- 说明本批关键日志/错误从哪里看。涉及数据迁移或不可逆副作用时提前准备相应恢复方法；代码提交不能代替数据备份。

产物：配置说明、测试数据/身份的取得方式、实际服务与连接目标、授权/验证状态。

## 6. 实际启动并取得最小验证反馈

新项目运行最小应用/命令入口，检查实际响应、退出状态或健康信号；必要时用浏览器访问。已有项目先验证与本批相关的基线，区分本来就失败和新增失败，不顺手修所有历史问题。

确认适用的格式、类型、测试或构建入口；复用现有检查，没有检查时只建立与当前技术和第一步行为相关的最小验证方式，并实际执行。脚本能运行但没有任何有效用例、零测试或仅返回成功码，不等于证明业务正确。未来功能不要求此时全部可测。

仅「启动供用户亲测」的任务到可访问性即止。完整初始化可以执行必要的启动/检查验证，但不能据此发起未经授权的付费或对外动作。

进程需留给用户操作时说明访问地址、必要配置、日志与停止方式；只为验证启动的临时进程检查完按需收尾。不能把已停止的服务描述为正在运行。

产物：实际运行命令、环境/版本、执行结果和证据入口。失败或无法验证时给出影响与下一定位动作。

## 7. 保存可续接的准备结果

project-context 记录稳定运行说明与准备状态，current-task 记录是否可开始本批，current-todo/当前执行记录保存版本现场、检查证据和下一步。不要在三处重复一份检查日志。

| 准备项 | 状态 | 证据/入口 | 缺口对第一步的影响 |
|---|---|---|---|
| 项目根与版本起点 | 已准备/阻塞/未验证/不适用 | | |
| 接手入口与有效约定 | | | |
| 技术骨架、依赖与配置 | | | |
| 测试数据/身份/必要服务 | | | |
| 实际启动 | | | |
| 适用检查入口与结果 | | | |

不适用的项可删去或简短说明。只有会影响当前第一步的缺口才阻塞它；必要条件满足后结束初始化。

## 提交给用户的结果应当具体

「仓库已准备」至少能落到：哪个目录/版本、怎样启动、怎样检查、第一步实现什么、查哪些文件、有什么仍不可验证。对于本次已授权的实现，准备就绪后可直接继续；前置准备请求则交付这些结果和必要选择。
